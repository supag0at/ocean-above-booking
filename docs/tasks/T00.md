# T00 脚手架与护栏

- 目标：把仓库骨架和自动护栏搭好，后面所有任务都在这套护栏下开发。**护栏本身要有测试。**
- 契约版本：v1.0-rc1（[CONTRACT-v1.md](../contracts/CONTRACT-v1.md)）。T00 不依赖契约的具体内容，只依赖目录和依赖规则（A-01 §1）。
- 范围：
  1. `git init`（本地，D-14）。`main` 分支的第一个提交收录现有的 `docs/`、`spikes/S-01/`（不含 `node_modules`、`out`）、题目原文和 `locations.db`。`.gitignore` 必须忽略：`.env`、`infra/secrets/*`（`*.example` 除外）、`node_modules`、构建产物。
  2. pnpm workspace，Node 24 LTS（D-21）。按 A-01 §1.1 建立目录骨架，每个包只放一个能编译的空入口和 `package.json`。根目录放 `tsconfig` 基础配置、eslint（禁止使用 `child_process`、`vm`、`eval`）和 prettier。
  3. `.npmrc`：`ignore-scripts=true`，加上 S-01 用过的 `min-release-age` 等价设置（H-09）。依赖用精确版本。**T00 只安装工具链依赖**（typescript、eslint、prettier、dependency-cruiser、vitest），业务依赖统一由 T01 安装。
  4. dependency-cruiser：把 A-01 §1.2 的依赖规则表**逐条**翻译成规则；`apps/web` 只能 import `@fb/contracts/web`（R-U1）。
  5. `scripts/`：
     - `check`：等于 `pnpm check`，依次跑 typecheck、lint、depcruise、test、hash、secrets、manifest；
     - `hash`：校验 `locations.db` 的 sha256；
     - `secrets`：扫描密钥，包括 DeepSeek key 的格式，以及 `-----BEGIN` 这类私钥头；
     - `manifest`：读取 `docs/tasks/<ID>.manifest`，检查当前分支的改动是否只落在白名单路径内；同一个 manifest 里不能同时出现前端路径和后端路径（R-U1，归属见 A-01 §1.3）。
  6. git hooks（`.githooks/`，用 `core.hooksPath` 启用）：
     - pre-commit：跑 `secrets`、`hash`、`manifest`；
     - 受保护路径只有 `main` 分支（父会话）能改，其他分支一旦改到就拒绝提交。受保护路径包括：`packages/contracts/**`、`docs/contracts/**`、`docs/adr/**`、`docs/planning/**`、lockfile、根目录 `package.json` 的依赖段、`.npmrc`、`locations.db`。
     - 分支名决定当前任务：`task/<ID>` 或 `task/<ID>/<子块>`，hook 据此找到对应的 manifest。
  7. `infra/compose/compose.yml` 骨架：列出 8 个服务、按 A-01 §2.2 的网络分段、按 A-01 §2.3 的 secrets 声明（只写 `*.example`，不写真值）。镜像和启动命令可以先用占位，**但网络和 secrets 的声明必须是最终形态**，因为 CT-04 和 CT-05 要用它们来测。
  8. worktree 约定：写一个脚本 `scripts/new-worktree <ID>`，在 `..\flight-booking-wt\<ID>` 创建 worktree，分支为 `task/<ID>`（D-15）。
- **护栏测试**（必须有，放在 `scripts/__tests__/`）：
  - 修改受保护路径时，提交被拒绝；
  - 提交 manifest 之外的文件时，被拒绝；
  - 同时修改前端和后端路径时，被拒绝；
  - 提交一个看起来像密钥的字符串时，被拒绝；
  - `locations.db` 被改动一个字节后，`hash` 失败；
  - dependency-cruiser：在临时目录里构造一个"harness import pg"的样例，规则必须报错。

  每条都要先断言"场景前提成立"，再断言"被拦住了"。
- 运行时约束：只碰本任务列出的路径。不读取 `.env` 的值。不安装业务依赖。
- 只能改（manifest）：根目录配置文件、`apps/*/package.json` 和空入口、`services/*/package.json` 和空入口、`packages/*/package.json` 和空入口（**`packages/contracts` 只建空壳，内容由 T01 写**）、`scripts/**`、`.githooks/**`、`infra/compose/**`、`infra/secrets/*.example`、`.gitignore`、`.npmrc`、`README.md`（只写开发环境怎么起）。
  - T00 是第一个任务，它自己的提交发生在受保护规则生效之前，所以第一个提交直接提交在 `main` 上。后续提交走 `task/T00` 分支。
- 依赖边：依赖 G0 ✅；被 T01 依赖。与 C-01 契约合并（父会话）并行。
- 验收标准：
  1. `pnpm check` 在空骨架上全部通过；
  2. 上面 6 条护栏测试全部通过，并且能复现；
  3. `git log` 里第一个提交包含现有文档，`.env` 不在仓库里；
  4. `docker compose -f infra/compose/compose.yml config` 能通过，网络和 secrets 的声明和 A-01 §2.2、§2.3 逐条一致。
- 执行单元：②½ 新开，任务负责人用 T2（Opus 5.5 medium）。按 R-U3，配置样板、各个空包这类边界清楚的子块，可以交给 Sonnet 子 agent。
- 验收方：父会话核对实际产出，再派 ① T2 做正交验收（重点是护栏测试有没有真的拦住）。
- 禁止：往 `packages/contracts` 里写内容；安装业务依赖；改 `docs/` 里已有的文件（新建 `README.md` 除外）；推送到远程。

### 新发现
- **S-16 已确认**：pnpm 12.21.0 **完全不读** `.npmrc` 里的 `ignore-scripts` / `minimum-release-age` / `save-exact`（`pnpm config get` 返回 undefined），只读 `pnpm-workspace.yaml` 的 `ignoreScripts` / `minimumReleaseAge`（分钟）。所以 H-09 的有效配置在 `pnpm-workspace.yaml`（`ignoreScripts: true`、`minimumReleaseAge: 2880`、`savePrefix: ''`），`.npmrc` 保留同义设置给 npm 用。`scripts/supply.ts` 两处都检查，并检查所有 package.json 和 lockfile 的 specifier 都是精确版本。
- `savePrefix: ''` 不会改写显式范围（`pnpm add @types/node@24` 仍写成 `^24.19.2`），已手改为精确版本；supply 检查会拦住这种情况。
- 工具链版本：typescript **6.0.3**（不是 7.x：typescript-eslint 8.72.2 的 peer 是 `<6.1.0`）、eslint 10.15.0、@eslint/js 10.0.1、typescript-eslint 8.72.2、prettier 3.10.1、dependency-cruiser 18.7.2、vitest 5.1.0；另装了 **vite 8.3.8**（vitest 5 把 vite 改成了必需 peer）和 @types/node 24.19.2。全部发布满 2 天以上。
- 本机 Node 是 **22.23.5**，不是 D-21 的 24。工具链和脚本在 22 上都能跑（脚本靠 Node 的 type stripping 直接跑 .ts）；`engines.node >=24` 只是声明，pnpm 不阻止安装。生产镜像用 node:24。
- `docker compose config` 不要求真实 secret 文件存在，所以 CT-04/05 可以在没有 secrets 的机器上跑。
- 本地 hook 只是"第一道"：`--no-verify`、或在 worktree 里改 `scripts/` 都能绕过。真正的关口是**父会话合并前在 main 的 checkout 里跑** `node scripts/manifest.ts --branch task/<ID>`（用 main 的护栏代码检查任务分支的提交），再跑 `pnpm check`。已写进 README。
- manifest 一律从 `main` 读取（main 上没有时才退回工作区），任务分支改自己的 manifest 不起作用。
- 委派（R-U3）：没有委派给 Sonnet。各包空壳和配置样板用一个脚本循环生成，比写委派说明更快；护栏逻辑、depcruise 规则、compose 网络和 secrets 都是我自己写的。
