公共规则见 [W3-common.md](W3-common.md)。

- **目标**：实现 `services/harness`。它是一个无状态的 BullMQ worker：被唤醒后拿到租约，从事件日志确定性地投影出上下文，用 pi-agent-core 跑一次运行，把事件写回 session，最后释放租约。
- **规范**：**A-02 全文**，重点是：
  - §2（事件和 `agent.message` 字段、过程区）
  - §3（唤醒、租约和 fence 的 Lua 脚本、computeWork、运行步骤、结局表、崩溃恢复、messageKey）
  - §4（projector 按运行分段、渲染格式、system 消息、compactor）
  - §5（execute 信封）
  - §6（pi 适配层、配置、坑和对策、§6.5 开工后第一批验证）
  - §8（数字守卫、已出票声明守卫、标签守卫。**§8.7 的打码已作废**，见 CONTRACT M-2）
  - §10–§12（语言、提示词、失败语义）
  - §19（T09 走查时提出的 26 个问题和答案）

  另外参考 S-01 的 REPORT.md、R-02、CONTRACT-v1 的 M-2、M-4、M-6、M-14、M-16、M-17、M-18，以及 A-01 §5.1（session API）和 §7.1–§7.3（Redis 和门铃）。
- **要点**：
  - harness **没有数据库凭证，网络上也到不了 booking**。
  - pi 固定使用 1.5.2：用 `initialState.messages` 加 `continue()` 重建上下文。
  - `beforeToolCall` 的第一步对原始参数做 `Value.Check`（CT-08）。
  - 缺失的工具结果由 harness 自己补齐：先重放，失败再补 interrupted（D-47）。
  - `max_tokens` 设为 4096；推理档位用低档；不使用 strict。
  - 默认并行执行工具，有副作用的工具串行（D-44）。
  - projector 只做投影，compactor 是独立组件（D-52）。
  - 过程区的文字和推理增量**不打码**，照常推送（M-2、M-4）。
- **替身**：
  - session API 用一个假的 HTTP 服务，按契约实现，可以从事件数组装出来；
  - hands 用假的 execute，返回固定的工具结果；
  - Redis 用 docker 跑真实实例；
  - DeepSeek 在单元测试里用 pi-ai 的 mock 或者 faux provider。真实调用只用于 §6.5 的验证和少量冒烟测试，**总共不超过 50 次**，key 只能从 `.env` 读取。
- **验收**：
  1. computeWork 和 projector 的单元测试。
  2. **CT-12** 前缀性质测试：较早截断点的投影结果，必须是较晚截断点投影结果的前缀。用 fast-check 做。
  3. 黄金往返测试：重放出来的请求和第一次运行时真实发出的请求逐字节一致。
  4. 租约和 fence：多余的门铃不会误杀正在运行的持有者；过期的 worker 写入会被拒绝。
  5. 崩溃测试：在工具执行期间杀掉 worker，另一个 worker 接手，日志里工具调用和结果的配对完整。
  6. 守卫：用户说"应该是 $1"时会被拦截；最终回复里出现没有来源的数字会被拦截。
  7. §6.5 的验证项逐条给出结论。
  8. 给人工验收准备入口：一个脚本，对着替身跑完一段完整对话，打印出事件日志。
- **执行**：②½，负责人用 T2。pi 适配层的黄金测试、projector 的性质测试可以交给 Sonnet。租约、fence、恢复这些逻辑由负责人自己写。

- **CT-12 compaction 变体时好时坏的根因**：生成器 `buildLog` 的 compact 步骤允许"边界 ≥ 上一次边界"，所以偶尔会写出两条 `compactionId` 和幂等键都相同的 `agent.context_compacted`（反例里是 seq 4 和 seq 8 都是 `compact:cmp_run_…01`）。真实系统里这种日志不可能出现：A-01 §3.2 有 `UNIQUE (session_id, idempotency_key)`，session API 会去重；compactor 自己也从不重复同一个边界（`compactor.ts`：边界等于上次边界就返回 null）。两条事件的 `ts` 不同，所以摘要消息的字节不同，前缀断言失败。只有随机种子刚好生成"重复边界"时才会出现，所以时好时坏。修法：生成器改成边界**严格前进**，`buildLog` 末尾断言幂等键唯一（违反就抛错）。断言本身没有改、没有放宽，也没有固定种子或减少运行次数。验证：把生成器临时改回旧写法，新加的唯一性断言马上报 `duplicate idempotencyKey compact:cmp_run_…`；用新生成器连续跑了 10 次 `prefix.property.test.ts`，10/10 通过（compaction 变体每次 200 个样本）。
- **真实 Redis 上的崩溃接手测试**（我自己写的）：新增 `test/recovery.redis.test.ts`。租约 Lua、fence、ephemeral publish 都走 docker 里的 redis:7；替身 session API 从真实 Redis 读 fence。原来的 `recovery.test.ts`（FakeRedis + 假时钟）保留。
- **60s 单次请求计时器改为符合 A-02 §3.5 原文**：上一位执行者让它从"请求发出"（onPayload）开始计时，但 §3.5 写的是"从 assistant 的 `message_start` 开始，到 `message_end` 清掉"。现在按原文实现；从没开始流式返回的请求由 120s 的运行计时器兜底（M-23 ③：哪个先到算哪个）。新增两个测试：流在 `message_start` 之后卡住会触发 request_timeout，并重试 2 次；请求一直没有响应时，只会触发 RUN_TIMEOUT。我做了变异验证：把计时器改回旧写法，第二个测试就失败。
