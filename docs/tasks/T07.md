# T07 booking（人工单独验收，D-19）

公共规则见 [W3-common.md](W3-common.md)。

- **目标**：实现 `services/booking`。这是**唯一**能写 `tickets` 表的进程，只接受 gateway 通过内网发来的确认下单请求。
- **规范**：
  - A-01 §2.2（只加入 db_booking 网络；端口 8083；来源检查只允许 gateway）
  - A-01 §2.3（凭证：只有 booking 的数据库凭证和服务间 token）
  - A-01 §3.3（booking 的数据库授权）
  - A-01 §5.2（确认链路 a–f 步，以及失败表）
  - A-01 §5.4（booking API）
  - A-01 §11
  - CONTRACT-v1 M-6、M-12、M-21
- **要点**：
  - 校验三件事：报价属于这个会话的用户；报价出示过（以 `quote_offers` 为准）；报价没有被用过。报价不过期（D-10）。
  - 出票写入和"一个报价只能用一次"必须在**同一个事务**里完成，靠 `tickets.quote_id` 的唯一约束保证。
  - 幂等：同一个报价重复确认时，返回第一次的出票结果，不报错，也不重复出票。
  - 服务间 token 从 `SecretProvider` 读取，不能从环境变量读。
  - **不写 events**，事件由 gateway 写（M-21）。
- **替身**：不需要。Postgres 用 docker 跑真实实例。
- **验收**：
  1. 正常出票。
  2. 下列情况每种都要返回规定的错误码：别人的报价、没出示过的报价、不存在的报价、已经用过的报价。
  3. **并发**：同一个报价同时发 20 个确认请求，只出一张票，其余都返回第一次的结果。
  4. 不带 token、或者 token 错误时返回 401；来源地址不在白名单时返回 403。
  5. 用 grep 检查：除了 booking，任何地方的代码里都没有 INSERT tickets。
  6. 给人工验收准备好入口：一条命令或一个脚本，能演示正常出票、重复出票和并发出票。
- **执行**：②½，任务负责人 T2。**核心事务逻辑由负责人自己写**，测试用例可以交给 Sonnet。

### 人工验收入口
```bash
node services/booking/scripts/demo.ts
```
需要 Docker Desktop 在运行、本地已有 `postgres:16` 镜像。脚本会起一个临时 Postgres（用 `infra/db/init/00-roles.sh` 建真实角色、迁移和授权），以 `fb_booking` 角色在 127.0.0.1 上跑真实的 booking HTTP 服务，依次演示：正常出票、重复出票、同一报价 20 个并发确认、各种错误码、token 和来源检查，最后打印 tickets 表并确认 events 表为空。全部通过时退出码为 0（`20/20 checks passed`），结束时删除容器。
完整测试：`npx vitest run services/booking`（54 个用例，约 25 秒）。

### 实现要点（`services/booking/src/`）
- `booking.ts`（负责人亲自写）：一个 READ COMMITTED 事务完成 A-01 §5.2 a–d。a 查 `quotes WHERE id AND user_id`，没有就 not_found（别人的和不存在的不可区分）；b 查 `quote_offers`（quote_id + quotes.session_id），没有就 not_offered；c `INSERT … ON CONFLICT (quote_id) DO NOTHING RETURNING`。"报价是否已用"**只由这条 INSERT 和 `tickets.quote_id` 唯一约束决定**，不存在先读后写的窗口；冲突时用新语句（新快照）读出第一张票，返回 alreadyBooked。id / ticket_no 随机碰撞用 SAVEPOINT 换 id 重试，最多 3 次（S-13）。价格和距离从报价 payload 原样复制，payload 损坏（quoteId 不符、数字类型不对）直接拒绝（500），不出票。不写 events（M-21）。
- `server.ts`：检查顺序为来源地址（403 FORBIDDEN_PEER，platform 钩子）→ Bearer token（401，用 sha256 后 `timingSafeEqual` 做常量时间比较，在解析 body 之前）→ 严格 schema（400）→ 事务。数据库不可用 → 503 SERVICE_UNAVAILABLE；权限错误（42501）等其他异常 → 500 INTERNAL，不当成可重试。
- `config.ts` / `main.ts`：token 和数据库密码只从 `FileSecretProvider`（/run/secrets）读取，启动时预读，缺文件就启动失败；绑定地址拒绝通配。

### 新发现
1. **和 T07.md 验收第 2 条有出入**：第 2 条要求"已经用过的报价"返回规定的错误码，但契约里没有这样的码。A-01 §5.2 / §5.4 和 T07 要点"幂等"都规定重复确认返回 200 `{ ticket, alreadyBooked: true }`，不报错。我按契约实现（第 1 优先级以上的规范来源）。如果本意是别的，请父会话裁定。
2. **测试环境**：`services/` 下禁止 `child_process`，所以测试和 demo 通过 Docker Engine 的 HTTP API（Windows 命名管道 / unix socket）起容器，不用 docker CLI。没有 Docker 时 booking 的数据库测试会跳过（和 CT-06 一样），并打印 `[T07] SKIPPED` 警告。
3. **CT-06 偶发失败**：在完整 `pnpm check` 里有一次 `scripts/__tests__/db-grants.test.ts`（T01 的）失败，容器内 `pg_ctl: server did not start in time`（Postgres 其实已经就绪）。单独重跑 18/18 通过，再跑完整 check 也通过。可能和多个 W3 会话同时起容器、机器负载高有关，不是 T07 的问题，我没有改它。
4. booking 不能直接依赖 `typebox`（依赖规则只允许 contracts + platform），所以没用 `@fb/platform/config.loadConfig`，自己写了一个小的配置读取（同样不在错误信息里回显值）。
