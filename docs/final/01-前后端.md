# 前后端

日期：2026-11-22。这是交给阅卷的终稿，过程设计仍在 [A-01](../design/A-01-frontend-backend.md)。Agent、工具和评测见 [02-agent与评测](./02-agent与评测.md)。

线上地址：https://g0at.top 。登录只填用户名。

## The architecture and data flow of the app

浏览器只和 Caddy 说话。Caddy 提供前端静态页，并把 `/api` 转到 gateway。TLS 停在 Cloudflare，源站保持 HTTP。公网入口是这台一直开着 Docker 的 Windows 电脑，cloudflared 把 `g0at.top` 转到本机 80 端口。

一次订票经过这些进程：

1. 用户用用户名登录。gateway 在 Redis 里建立会话，浏览器拿到 httpOnly 的 `fb_sid`，以及给后续写请求用的 CSRF cookie。
2. 用户发出一句话。gateway 把 `user.message` 追加进 Postgres 事件日志，再往 Redis 队列放一个唤醒。
3. harness 取出唤醒，调用 DeepSeek，需要查航线或票时调用 hands。
4. hands 只读 `locations.db`，算出报价并写入自己的表。它不能写机票。
5. 前端收到「出示报价」事件后，按 quoteId 再请求 `GET /api/v1/quotes/:quoteId`，用返回的结构化数据画报价卡。
6. 用户点击报价卡上的确认。这个请求带会话 cookie、CSRF 和 `Origin: https://g0at.top`，由 gateway 转到 booking。booking 是唯一能写入机票表的进程。

数据分成四块：

| 数据 | 谁拥有 | 规则 |
|---|---|---|
| `locations.db` | hands 只读加载 | 启动时核对 sha256 `fc4134475ab5d0b0d1e2c2ab081b4a41da59dbdb25ff7ee147b935d33007386f`，不一致就拒绝启动 |
| 会话事件 | gateway | 只追加。用户消息、工具结果、出票结果都在这里 |
| 报价 | hands | 写入后不改。报价不过期，同一会话里每个报价只能成交一次 |
| 机票 | booking | 只有确认请求能插入 |

harness 拿不到数据库口令，也拿不到 booking 的服务凭证，网络上也到不了 booking。DeepSeek 的密钥只在 harness。密钥以文件挂进容器，不写进环境变量，也不进 git。

## How routes, distances and prices are computed

城市、坐标和航线只来自 `locations.db`。直飞只存在于两种边：`hub_links` 里的两个枢纽，以及非枢纽城市和它 `connected_hubs` 里的每个枢纽。边是双向的。换乘只发生在枢纽，所以路径中间的城市都必须是枢纽。没有直飞时，取总距离最短的一条路，整条路出一张票。

一段的距离是两端坐标的欧氏距离，单位是公里。票的飞行距离是各段距离之和，保留未舍入的和。价格是 `Math.round(总距离公里 × 13)` 美分，也就是每公里 0.13 美元，对正数是四舍五入。界面上距离和美元都显示两位小数。各段各自四舍五入后再相加，可能和总距离的两位小数差 0.01 公里；总价始终按未舍入的总距离计算。

两条路的距离差小于 `1e-6` 公里时视为一样长。之后比航段数，再比城市名的码点顺序。

报价接口只接受库里的 `city_name` 原文，比较前做 NFC。`shanghai` 这种全小写不会被当成 Shanghai。没有航班的城市会带上最近的有航班城市。最近城市按欧氏距离，距离相同时按城市名字典序。

## How you make sure the numbers shown to the user are correct

用户看到的价格在报价卡上。卡片的数据来自 `GET /api/v1/quotes/:quoteId`，也就是 hands 落库的那一份。聊天文字里的数字不作为报价。过程区会短暂显示模型的中间文字，界面标明这些文字不是报价依据。

确定性核对见下一份文档的 Evaluation：490700 对有序城市对上，本实现和独立 oracle 的路径、价格、距离一致；203 条确定性用例全部通过。

## How you make sure nothing is booked without the user's confirmation

出票只来自用户点击报价卡上的确认按钮。这个请求要同时满足：

- 浏览器会话 cookie
- CSRF
- `Origin` 等于配置的 `PUBLIC_ORIGIN`（线上是 `https://g0at.top`）
- 报价属于这个会话
- 这张报价还没有出过票

同一张报价再点一次，返回已经出过票，机票表仍然只有一张。用户在输入框里打「确认」或 “yes” 只会变成一条普通消息，不会调用 booking。

Agent 侧为什么没有出票工具，写在 [02-agent与评测](./02-agent与评测.md)。

## Known limitations and failure modes, and what you would do next

已经接受的限制：

- 登录只有用户名。知道用户名就能进入那个用户的会话。题目允许很简单的账号，正式产品要换成密码或第三方登录。
- 演示跑在一台常开的电脑上。这台电脑休眠、关机，或 Docker、隧道进程停掉，https://g0at.top 就不可用。电脑重启后容器可以自己起来，隧道进程要再启动。
- gateway、hands、booking 的健康检查把「在听」和「被同伴检查拒绝的 403」都看成健康。它不能证明数据库仍然可用。
- 报价不过期。演示里这样做，是为了刷新页面后同一张卡仍能确认。正式产品应给报价一个期限。
- 被攻破的 harness 能读会话、以活动会话的身份调用 hands，并向公网发出请求。它仍然没有机票库的写权限，也到不了 booking 所在的网络。
- 过程区里的推理文字可能出现模型自己估算的数字。这些文字不落库，刷新后消失，也不经过最终回复的数字守卫。

这一版不做退票、改签、真实支付、乘客信息、多城市行程和按用户限流。下一步会先补账号、报价有效期、能反映数据库状态的健康检查，以及让隧道在开机后自己起来。界面会在拿到参照后再改。
