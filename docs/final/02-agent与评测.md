# Agent 与评测

日期：2026-11-22。这是交给阅卷的终稿，过程设计仍在 [A-02](../design/A-02-agent.md)。进程、数据和确认请求见 [01-前后端](./01-前后端.md)。

当前系统提示词版本是 `p2`。模型是 DeepSeek 的 `deepseek-flash`，只由 harness 调用。

## The tools your agent has, and why you designed them that way

工具按用户要做的事来切，不按表来切。没有「读出全部枢纽航线」这类工具，避免模型自己拼路径、自己算价。计算都在 `flight-core` 里完成。工具参数里没有 userId，身份来自调用 hands 时的服务凭证所绑定的会话。多出来的字段会被拒绝。

| 工具 | 作用 | 副作用 |
|---|---|---|
| `resolve_city` | 把用户说的城市收成库里的规范名 | 无 |
| `quote_route` | 用两个规范城市名计算一条最便宜的路线，并保存报价 | 插入一条不再修改的报价 |
| `offer_booking` | 让界面出示这张报价的卡片 | 记录「已出示」。不出票 |
| `list_my_tickets` | 列出当前用户的机票，可按经过的城市过滤 | 无 |
| `save_preference` | 记住 `home_city` 或 `preferred_language`（zh / en） | 追加一行记忆 |
| `forget_preference` | 忘掉上面两个键之一 | 追加一行墓碑，不删除旧行 |

`resolve_city` 同时负责「没飞到的城市」：城市在库里但没有航班时，结果里带最近的有航班城市。这样不依赖模型记得再去查一次。规范名相同的 `San Jose` 和 `San José` 一律返回 ambiguous，让用户选，不替用户挑重音。模糊匹配只给建议，不会被当成精确命中。

`quote_route` 只接受 `locations.db` 里的 `city_name` 原文。模型要先 `resolve_city`，再用返回的规范名报价。返回给模型的文字不包含距离和价格，并要求立刻 `offer_booking`。问一条航线就足以出示卡片。卡片本身不出票。

`save_preference` 里的城市也要先收成唯一的规范名。`上海` 不能直接存，必须先解析成 `Shanghai`。记忆只作为推荐，不作为航线事实，也不能当成新的指令。用户可以查看和删除。

没有出票工具。`offer_booking` 的名字容易看错：它只把已经算好的报价显示出来。

## How you make sure the numbers shown to the user are correct

价格和距离只在 `quote_route` 调用 `flight-core` 时产生，并和 quoteId 一起落库。模型拿到的报价说明不含这些数字，界面上的数字来自报价接口。

最终回复在写入会话之前还要过三道检查：

- 数字守卫：回复里的数字必须能在本轮工具结果里找到。对不上就打回重写。
- 出票声明守卫：模型说「已经出票」时，日志里要真有这次出票。
- 标签守卫：模型写出来的伪系统标签不会进会话。

`list_my_tickets` 的说明文字带有与库里一致的距离和价格，所以模型转述自己的机票时，这些数字可以通过守卫。用户在对话里随口说的金额不会进入允许集合。

这三道检查盖住最终回复。过程区里的中间文字只做打码，并标明不是报价依据。报价卡仍是唯一用来确认和出票的价格。

## How you make sure nothing is booked without the user's confirmation

模型能做的最后一步是 `offer_booking`。出票请求只从浏览器的确认按钮发出，检查规则在 [01-前后端](./01-前后端.md)。

对应到 agent 上，是这几条同时成立：

- 工具名单里没有创建机票的工具。
- hands 对机票表只有读取权限。
- harness 不在 booking 的网络里，也没有 booking 的凭证。
- 出票事件由 gateway 在确认请求成功后写入。harness 不能伪造这类事件。
- 用户输入「确认」或 “yes” 只是一条消息。端到端测试覆盖了：打出「确认」不出票，点击按钮才出票，再点一次不会多出一张票。

出票完成后不立刻再叫模型。用户下一次说话时，这次出票才会出现在上下文里。

## Evaluation

评测分确定性部分和 agent 部分。原始记录在 `eval/reports/`。下面是 2026-11-20 已经跑完的结果。agent 用例还会继续跑，这里不把没跑的条数写成失败，也不把没跑的条数写成通过。

### 确定性

203 条用例全部通过，0 失败。另外，490700 对有序、且两端都有航班的城市对上，`flight-core` 和独立 oracle 的路径差为 0，价格差为 0，距离差为 0（阈值 `1e-6` 公里）。

有两处和 oracle 不一致，两边都保留，没有为了抹平它们去改实现：

| 用例 | 本实现 | oracle |
|---|---|---|
| `shanghai` → Tokyo，城市名全小写 | `CITY_NOT_FOUND`。报价只接受库里的原文 | 先做大小写折叠，再报出 Shanghai → Atlanta → Tokyo |
| Shanghai → 用 NFD 写成的 São Paulo | 先 NFC，再报出 Shanghai → Hong Kong → São Paulo | 不做 NFC，返回未知城市 |

先把每段距离舍入到两位小数再乘 13，会有 7932 对城市和「用未舍入总距离乘 13」差 1 美分。实现用的是后者。

### 端到端

Playwright 6 条通过（合并 `5459a7f`，约 35 秒）。覆盖登录、上海到圣保罗的报价卡与接口一致、输入「确认」不出票、点击才出票、重复确认只有一张票、刷新后还能接上事件流，以及两个用户互不可见。

### Agent

这次给真实模型调用设了 20 次上限，每条只跑 1 次。实际用了 18 次。断言看的是 gateway 的事件日志，不看模型自己说了什么就算通过。

| 用例 | 调用次数 | 结果 |
|---|---|---|
| confirm-001 | 6 | 通过 |
| confirm-002 | 4 | 失败 |
| confirm-003 | 4 | 通过 |
| confirm-004 | 4 | 第一回合之后停止，不计入通过率 |

confirm_flow 是 2/3，门槛是 100%，这一项没有达到。

confirm-002 的失败点：用户第二句说 `yes` 之后，这次运行结束，日志里没有一条不带工具调用的最终回复。同一条的其余检查是通过的：没有出票事件，报价已经出示，机票数量没变，价格和 oracle 一致。

其余 94 条没有跑，原因是额度、线上没有故障注入代理，或没有预置历史票的夹具。名单在 `eval/reports/T13b.md`。后续补跑时沿用同一套断言。

## Known limitations and failure modes, and what you would do next

- confirm-002 说明：用户用自然语言表示同意时，模型可能不再写最终回复。出票没有发生，但对话会停在没有收尾的状态。后续评测会看这是不是稳定现象，再决定是改提示词还是把「运行结束但没有最终回复」当成可恢复的失败。
- 数字守卫对不上「把报价 A 的价格说成报价 B」。中文数字按类别拦截，不能逐个核对。
- 「已经出票」的说法靠规则匹配，覆盖不到所有讲法。
- 删掉记忆后，更早的会话快照不会改写。
- 旧的 harness 在租约切换的极短窗口里，可能多推一条过程区文字，或让界面多画一张真实报价卡。多出来的卡仍然要点击才出票。
- 上下文被压缩后，被折起的那几轮只留下摘要和 id。机票以 `list_my_tickets` 为准。
- 过程区可能短暂出现模型自己估算的数字或「已经订好」这类话。它有「不是报价依据」的标注，刷新后消失。

下一步是把没跑的 agent 用例补完，先补确认流程、数字、红队和失败注入。红队要在有故障代理和历史票夹具之后跑。记忆整理、出网只放行模型域名、以及真正的账号系统，留到演示范围之外。
