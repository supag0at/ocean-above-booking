### 0.2 为什么可以这样合并
- **原来的 T05（数据库 schema）并入 T01**。A-01 已经把 DDL、角色和授权写到可以直接执行的程度，这些本身就是"数据归属"契约，应该和契约包一起冻结。T01 产出 `infra/db/migrations/`，后面每个服务都直接用同一份迁移文件。
- **T08 hands 不再等 T03 flight-core 完成**。T01 在契约包里定义 flight-core 的接口和类型，T08 先用一个替身实现开发，到 W4 再接入真实的 flight-core。T06 和 T07 也不再等 T05，迁移文件在 T01 就已经有了。
- **T00 和契约合并并行进行**。脚手架（git、workspace、lint、hook、compose 骨架）不依赖契约的具体内容。T01 要等 T00 完成，以及父会话把契约合并完。
- **G1 和 G2 合并**：契约冻结和地基验收在同一个关口一起完成。

### 0.3 执行规则（R-U3）
- **任务负责人往下委派**：W3 的任务如果比较大，又能拆出**边界清楚、不需要了解太多实现细节**的子块，比如某个模块的样板代码、一组测试、一个独立的纯函数或者组件，就由该任务的会话（任务负责人）继续往下派：
  - **会话内子 agent（①）**：结果要回到当前这一轮，而且做完就可以丢掉。例如：一组单元测试、某个组件、一段迁移脚本。
  - **从子会话 fork 出新会话（②）**：需要人中途查看，或者要跨很多轮。fork 出来的会话**必须用自己的 worktree**，分支从任务分支切出（`task/<ID>/<子块>`），由任务负责人合并回 `task/<ID>`。
- **写代码的子任务默认用 Sonnet 5.5**（T3）。任务负责人保留 T2（Opus 5.5 medium），负责拆分子块、把关运行时约束、审查子块的产出。子块遇到状态、并发、安全边界方面的判断时，不交给 Sonnet，由负责人自己处理或者上报。
- **委派不改变边界**：子块只能改本任务清单（manifest）里的路径；R-U1 仍然有效，前端和后端不能出现在同一个子块或同一个会话里；子块不能改契约、不能加依赖。
- **任务负责人对子块的结果负责**：合并之前要自己跑 `pnpm check`，并核对子块实际产出了什么，不能只看子块的汇报。父会话的验收对象是整个任务，不是单个子块。
- **验收**：设计文档不再复核（R-U2）。代码任务的验收流程不变（§6）：父会话核对实际产出，再派 ① 做正交验收。T07 和 T09 由人单独验收。

## 3. 会话职责

### 3.1 角色
| 角色 | 是谁 | 职责 | 不做什么 |
|---|---|---|---|
| **人（你）** | 用户 | 拍板所有决策；在 G0 到 G6 关口给结论；手动验收安全关键任务；把 DeepSeek key 写进本地 `.env` | — |
| **父会话 / 总控** | 本会话，全程不交接（D-17） | 写规划和任务规划；冻结和修改契约；派发任务；接收汇报并**核对实际产出**；派 ① 做验收；合并分支；广播契约变更；落盘记录；把决策交给人 | 不写业务代码（T01 契约包和 T16 文档除外）；不替人做决策；不把子会话的消息当成人的授权 |
| **设计会话**（A-01 / A-02） | ② fork，T1 | 在自己的文档范围内产出设计和契约草案；跨文档的接缝问题上报父会话 | 不改对方文档；不定契约终稿（由父会话合并）；不写代码 |
| **开发会话**（T03、T05–T11、T14、T15 …） | ②½ 新开（少数 ② fork） | 只做自己的任务，严格遵守任务规划里的"运行时约束"和"只能改的路径"；自检；写任务文档；按模板汇报 | 不改契约、不加依赖、不改别的任务的文件、不自己做决策；卡住就停下来上报 |
| **验收子 agent** | ①，至少 T2 | 只拿到验收标准、diff 和运行入口，自己复现证据，出验收报告 | 不改代码；拿不到开发过程 |
| **专项审查子 agent** | ①，T2 | 安全红队（T06/T07/T09/T10）、并发与崩溃审查；只出报告 | 不改代码 |
| **隔离实现子 agent**（T04） | ①，T3 | 只根据题目和契约写参考实现 | 看不到 flight-core 的代码 |

**R-U1（用户 2026-11-18）：前端代码和后端代码必须由不同的会话来写。**
- 写 `apps/web/` 的会话不能碰 `services/`、`packages/`（契约包除外，而且契约包只能读）；写后端的会话也不能碰 `apps/web/`。
- 这条由 T00 的路径白名单 hook 强制检查。T12 联调要拆成"前端适配"和"后端适配"两个会话。

### 3.2 执行单元怎么选（落到本项目）
- **A-01 / A-02 用 ② fork**：它们高度依赖本会话里讨论过的约束和决策，而且现在的对话历史还不算太长。
- **开发任务默认用 ②½ 新开**：边界由任务规划和契约讲清楚，不带规划会话的历史包袱，也减少被历史带偏。
- **所有验收、审查都用 ①**，并且不给开发过程。
- **T04 必须是隔离的 ①**：用来和 T03 做独立对拍，所以要防止同源错误。

### 3.3 模型档位（按 skill §5.1）
- T1（Opus 5.5 high）：A-01、A-02、契约 v1 合并、T01、契约变更的影响评估。
- T2（Opus 5.5 medium）：涉及状态、安全、正确性的模块（T03、T05–T10、T15），以及**全部验收**。
- T3（Sonnet 5.5 medium）：T04、T11、T13b、T14，以及样板代码。T3 遇到规划没覆盖的情况、要做取舍、或者连续两次修不好时，**停下来上报**，由父会话改派。

## 4. 版本控制（本地 git，D-14）

推荐方案（D-15）：**一个 monorepo + 每个开发会话一个 git worktree**。
- `main` 只有父会话能合并。每个任务在 `task/<ID>` 分支上开发，worktree 放在 `..\flight-booking-wt\<ID>`。
- 子会话**可以在自己的分支上提交**；父会话在验收通过后用 `--no-ff` 合并，提交信息里带上任务 ID 和验收报告路径。
- **路径白名单**：每个任务一个清单文件 `docs/tasks/<ID>.manifest`，写明只能改哪些路径。pre-commit hook 拒绝清单以外的改动。
- **受保护路径**（只有父会话能改）：
  - `docs/contracts/`、`packages/contracts/`
  - lockfile、`package.json` 的依赖段、`.npmrc`
  - `docs/adr/`、`docs/planning/`
  - `locations.db`（任何人都不能改，hook 校验哈希）
- 设计阶段（W1）还没有 git：A-01 和 A-02 写的是互不重叠的文件，不需要 worktree。T00 完成后，再把已有的文档作为第一个提交纳入 git。

|---|---|---|---|
| 子 → 父 | 完成 / 阻塞 | SendMessage，正文按第 7 节的汇报模板 | 阻塞类消息（契约变更请求、依赖申请、待决策）**发完就停下来等回复** |
| 父 → 子 | 追加指令、验收反馈 | SendMessage 发给原来那个会话 | 同一件事不另开新会话 |
| 父 → 多个子 | 契约变更广播 | SendMessage + `docs/contracts/CHANGELOG.md` | 写明版本号、改了什么、受影响的任务、要怎么调整 |
| 父 → 人 | 决策和关口 | 本会话 | 引用人的原话；没回复的不算通过 |

落盘位置：
- 任务规划和派发简报：`docs/tasks/<ID>.md`
- 子会话的汇报：子会话把汇报写进 `docs/tasks/<ID>.md` 的"汇报"一节，消息里只放摘要和路径
- 验收报告：`docs/reviews/<ID>-review.md`
- 契约版本：`docs/contracts/CHANGELOG.md`
- 决策：`docs/adr/decisions.md`

## 6. 验收流程（每个任务都走）

1. **执行者自检**：`pnpm check` 全部通过，每条验收标准都附上证据（命令和关键输出），任务文档写好。
2. **父会话核对实际产出**：看 diff 是否只改了白名单路径，检查是否全部通过，任务文档是否齐全。只看汇报不算。
3. **① 正交验收**（T2）：只给验收标准、diff 和运行入口。重点看异常场景、安全场景、运行时约束（进程隔离、无状态、数据归属）。
4. **安全关键任务额外做 ① 红队**：T06、T07、T09、T10。
5. 有问题就**发回原执行者修复** → 复核。
6. **人手动验收**：父会话给出入口（URL 或命令）。T07 和 T09 单独验，其他按波次在关口统一验（D-19）。
7. 合并进 `main`，更新总索引。

禁止：为了让测试通过去改测试或放宽断言；绕过护栏（误拦了就上报原因）。
